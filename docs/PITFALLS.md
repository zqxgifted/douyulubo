# 避坑清单与验收

[← 返回 README](../README.md) ｜ [配置](CONFIG.md) ｜ [接口](API.md)

这些是从一次真实的大批量归档里总结出来的经验，与具体主播无关。

## 下载

| 现象 | 原因 | 正确做法 |
|---|---|---|
| 旧 VOD 重新下载后反而更短 | 平台现行 m3u8 可能比原始录播短 | **重下载只用于补缺，不要替换旧母版**；用 `ffprobe` 时长对比 `raw_detail.duration_sec`（±3%） |
| 「文件过小」误报 | 固定 MB 阈值会误杀超短场次（如 488 秒 / 25MB 属正常） | 设 `min_file_mb=0` 或核时长；本项目已对 <15 分钟的段豁免 |
| 分片下载中断 | 网络 / 限流 | 分片 >10KB 视为已完成，重跑自动跳过；`config.concurrent` 别调太高 |
| 系统盘被写满 | ffmpeg / node 往系统临时目录写 | 批量脚本已把 `TMP` / `TEMP` 指向 `<work_dir>/tmp` |
| 取流失败 `error=7` | 签名脚本轮换 | `loadSigner()` 重新抓页面脚本；探测脚本已内置重载一次 |
| 拿到 master playlist | 部分源返回多码率索引 | `parsePlaylist()` 会抛错，需再取一层 media playlist |

## 数据与关联

- `raw_detail.json` 是**对象**（key = `hash_id`），不是数组
- 关联场次一律用 `hash_id`，不要用 `title` 里的日期（存在标签笔误、多段连播、`-1`/`-2` 后缀）
- `point_id` 必须在 step2 里保存下来，否则 step3 / step4 都跑不了
- 分段场次各自有独立弹幕，不要当重复删掉

## 画质 / 体积核查

- `est_size` 是推算值，实测 ±5~10%、平均低估约 3%
- 判据建议：`实际大小 ≥ est_size` 视为足料；`0.8~0.95` 可选重下；`<0.8` 明显偏低
- **不要用 ±1MB 判据**（对 2GB 文件，5% 就是 100MB）
- `step5_probe_quality_all.js` 只查元数据不下载，用来判断现有文件是否最高档

## 弹幕

- 每个分段 1 个 XML（+ 可选 1 个 ASS），文件名与视频**完全一致**
- 0 条弹幕的场次不生成文件；生成后可用体积 >200 字节做基本校验
- XML → ASS 依赖 [DanmakuFactory](https://github.com/hihkm/DanmakuFactory) 的 CLI，
  路径通过配置提供，不要写进代码

## 验收清单

### 视频

- [ ] `raw_detail.json` 段数 = 已下载视频文件数
- [ ] 每个场次至少 1 个视频文件
- [ ] 重下载文件 `ffprobe` 时长 vs `duration_sec` 偏差 ≤ 3%
- [ ] 没有跨场次内容重复（用本地真 md5 比对）
- [ ] 没有 `.ts` 残留（除该场次本身只有 ts）
- [ ] 没有 `(1)` 之类的副本

### 弹幕

- [ ] 每段视频有且仅有 1 个 XML（+ 可选 1 个 ASS）
- [ ] 没有 0 条 / 0KB 的弹幕文件
- [ ] 分段场次（`-1` / `-2`）各自有独立弹幕
- [ ] 同一场次多版本时，保留弹幕更多且命名与视频一致的那份

### 运维

- [ ] 临时文件都在 `<work_dir>/tmp`，系统盘没被写
- [ ] 批量下载结束时工作盘剩余空间充足
- [ ] 失败清单 `downloads/_failed.txt` 已处理
